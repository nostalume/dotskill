# Visualization Design

Own how accepted information becomes a perceivable, honest and useful visual
representation. The domain, research or data owner retains authority over facts,
measurements and conclusions. The user owns purpose, reserved choices and
acceptance of taste. The current project owns its source, design system, formats,
dependencies and accepted edits. A renderer or provider owns its effects but does
not establish semantic or visual correctness by succeeding.

Establish whether the request is creation, revision, review, rendering or a
combination. Review-only work does not authorize edits. A style change does not
authorize changing meaning, data, interaction or timing; a format name alone does
not select this skill. Use the native container owner for document mechanics, the
analysis/research owner for new conclusions, and the software owner for generic
application behavior.

## Maintain the whole

Form a working visual contract from the evidence already available:

```text
purpose + audience/context + intended response
  -> authoritative information + failure conditions + preservation
  -> information structure
  -> representation hypothesis + material loss
  -> contextual quality criteria
  -> required and available execution capabilities
  -> editable source or output
  -> observation + critique
  -> revise any contradicted upstream judgment
```

Treat this as revisable reasoning, not a required form or state file. Inspect an
existing project, source and current output before asking for information they
already supply. Ask only when a missing decision is material, belongs to the user
or source owner, and would change the result. Otherwise state a reversible
hypothesis where it matters and proceed. Persist project-specific visual direction
only when collaboration, repeated production or maintenance has an actual need for
it; it remains project-owned and may evolve.

When the visual form, encoding or hierarchy is open, use
[representation selection](references/representation-selection.md) to construct
and compare hypotheses from the information structure. Use
[quality evaluation](references/quality-evaluation.md) to establish contextual
criteria, critique the actual result and decide which evidence supports completion.
For a precise revision, existing project decisions may already satisfy both
branches; reload only the guidance affected by the change.

Before selecting or changing a tool, project environment, framework, template,
asset, renderer, runtime, encoder or external provider, read
[execution and effects](references/execution-effects.md). It maps the accepted
postcondition to required capabilities, obtainable evidence and the strongest
honest completion claim.

For animation, timed media, deterministic capture or interactive state, read
[temporal and interaction design](references/temporal-interaction.md) after
establishing that time or interaction improves the intended meaning. Its maintained
HTML example is one bounded operation, not the default visual system.

## Create, revise and evaluate

1. Identify what the audience must understand, compare, decide, do or experience,
   plus what would make the visual misleading, unusable or unsuccessful.
2. Classify the information as quantitative, relational, spatial, sequential,
   temporal, interactive or explanatory; compose structures without erasing their
   distinct meaning.
3. Select an encoding and carrier that preserve applicable invariants. Treat
   hierarchy, density, style, pacing and interaction as contextual variables, not
   universal fixed values.
4. Choose an implementation only after the required source, editability, fidelity
   and evidence are known. Reuse compatible project capabilities; keep frameworks,
   templates, assets and providers conditional.
5. Create or revise within the admitted project boundary. Preserve direct edits
   and source identity, and keep deterministic decisions separate from effects.
6. Inspect the exact current source and every output state needed by the claim.
   Repair local defects; when evidence contradicts the representation or purpose,
   revise that upstream decision instead of polishing the symptom.

User agreement defines intent and acceptance policy; it does not prove that the
artifact satisfies them. Semantic or structural checks cannot prove appearance.
A still cannot prove motion or interaction. A successful render cannot prove data
truth. Claim only the quality supported by evidence from the current revision.

When required execution or observation is unavailable, use a compatible
alternative, return an executable specification or editable source with its
unverified obligations, request missing material authority, or report precise
unavailability. A strong handoff is complete only when the accepted result is a
handoff; do not relabel it as a verified final artifact.

## Hard gates

- Preserve accepted data, units, relationships, uncertainty, qualifications and
  source authority across every visual transformation.
- Do not promote a template, example, aesthetic preference, framework or current
  tool into universal policy.
- Do not force a full intake for a precise revision or serialize working state
  without a real consumer.
- Do not upload content, install dependencies, generate paid media, publish, or
  mutate an external destination merely because a capability is connected.
- Keep unavailable, partial, structurally checked, rendered, temporally inspected,
  interactively exercised and accepted results distinct.
- Return editable source and requested outputs, checks performed, unverified
  obligations and material limitations. Close only owned disposable resources.
